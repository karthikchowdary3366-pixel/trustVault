# TrustVault threat model

## Security boundary and design

The server is the authorization boundary. Each document has exactly one owner and zero or more explicit grants keyed by document and username. There is no public link or admin override. A `READ` grant permits opening and downloading; an `EDIT` grant additionally permits metadata changes and uploading an edited replacement file; the owner may also delegate `DELETE` per grant. Only the owner may grant/revoke. Folders can be shared with viewers so they can *list* the folder's documents, but folder access never lets a viewer open, download, edit, or delete a document: that always needs an individual document grant. The visible-document query is scoped before search filters are applied, and every open/download/edit/replace/delete/share service operation repeats its own check against current database state. Admin access is restricted to user management and audit screens.

Document bytes are stored outside web resources at a generated UUID storage key. The original filename is not used as a path. Upload type is checked using an allowlist (PDF, PNG, JPEG, TXT, DOC, DOCX, XLS, XLSX) plus content signature validation, with a 10 MiB cap. Open/download responses carry `X-Content-Type-Options: nosniff`. A replacement upload must keep the original content type. CSRF protection is enabled by Spring Security. The acting user in every audit row comes from the authenticated server-side identity, never from request parameters. Refused open/download/edit-page/delete shows a "not granted" page (403); edit submissions, grants and unauthenticated requests return 404.

## Attacker view: threat, example attack, defense

| Threat | Example attack | Defense implemented |
|---|---|---|
| IDOR | Ravi changes document ID 105 to 106 in a request | Per-request owner/grant check in the service layer; denial audited |
| Privilege escalation | User adds `role=ADMIN` to registration | No role field accepted; roles assigned server-side; `/admin/**` is ADMIN-only |
| Leaked file URL | Copied `/documents/5/download` opened without login or by another user | Private storage; no bearer URLs; auth + grant checked each request |
| Stale access | Revoked viewer reuses an old page or link | Grants read from DB on every request; no tokens/caches |
| Audit tampering | DB user edits or deletes audit rows | HMAC-chained events plus chain head; verified in admin view |
| Malicious upload | `.exe` renamed to `.pdf`, or oversized file | Extension allowlist, magic-byte check, 10 MiB cap, random storage key, nosniff |
| Search data leakage | Search reveals other owners' filenames | Search scoped to visible documents; only limited metadata exposed |
| Concurrent permission changes | Access revoked while a download is in flight | Revocation applies from the next request; an in-flight request finishes under the permission it started with |
| CSRF | Hostile site posts delete/grant | Spring CSRF tokens on all POSTs; rejections audited |
| Audit spoofing | Request carries a forged actor ID | Actor derived from the authenticated principal only |
| Delegated-rights abuse | Viewer with EDIT replaces a document with another file type | Replacement must match original type and passes the same validation; audited as an edit |
| Folder-grant bypass | Viewer with folder access opens a document in it | Folder grant only lists; document actions need a document grant |

## Threats addressed and regression coverage

| Threat | Mitigation | Test/evidence |
|---|---|---|
| Guess or reuse another document ID to view metadata or download | Owner/current grant check in service for every route; inaccessible IDs return the same 404 as missing IDs | `viewerCannotViewOrDownloadUnsharedDocumentAndAttemptIsAudited` |
| Change, delete, grant, or revoke against another owner's document | Edit and owner-only checks are separate; the admin role is not an implicit bypass | `viewerCannotEditDeleteOrGrantOnUnsharedDocument`, `administratorDoesNotAutomaticallyGainDocumentReadAccess` |
| Use an old access grant after revocation | Grants are loaded from the database on each request; no link/token/cache exists | `grantAndRevocationTakeEffectOnTheNextRequest` |
| Self-assign OWNER or ADMIN during public sign-up, or call admin account/role routes as a viewer | Public registration assigns VIEWER and does not accept a role field; only ADMIN can create VIEWER/OWNER accounts or demote an OWNER to VIEWER; admins cannot promote existing Viewers; ADMIN is only provisioned through operator bootstrap on an empty database; denied admin management attempts are audited | `RegistrationTests`, `AdminUserManagementTests` |
| Delete an account that owns documents or has active grants | Deletion removes grants to the account and requires transferring owned documents to another OWNER; admins cannot delete themselves or the last admin account; successful changes are audited | `AdminUserManagementTests` |
| Continue using an account after an administrator suspends it | A security filter checks account status on every request, invalidates the current session, blocks new logins, and audits blocked requests; grants are retained for possible reactivation | `accountDeactivationBlocksExistingSessionsAndCanBeReversed` |
| Take over a different account by changing profile details | Account settings only update the authenticated account; password changes require the current password, username changes require a unique valid name and end the current session, and email verification requires an expiring one-time code sent to the account's current or newly supplied address | `AccountSettingsController`, `AccountProfileService`, `AccountEmailVerificationService` |
| Discover confidential details through document search | Search intentionally exposes only document name, category, owner username, upload date, and access status to authenticated users; descriptions and file contents remain hidden, and every open/download/edit/delete request checks current permission | `DocumentAuthorizationTests`, `DocumentService` |
| View another owner's documents or activity through owner workspace routes | Owner-only routes check the signed-in role; uploads are filtered by current ownership and audit events by the IDs of documents currently owned by that account | `DocumentAuthorizationTests`, `OwnerController` |
| Create a public account without controlling its email address or accepting the terms | Public registration creates only a pending record until a six-digit email OTP is verified; the registration form requires agreement to the linked terms, and the accepted terms version/time is stored with the account. Admin-provisioned accounts intentionally bypass public verification and rely on administrator trust; they require an initial-password change prompt after first use | `accountIsCreatedOnlyAfterCorrectEmailOtpAndTermsAcceptanceIsRecorded`, `registrationRejectsMissingTermsAndWeakPasswords`, `AdminUserManagementTests` |
| Guess a registration OTP or reuse it | OTP is HMAC-protected at rest, expires after ten minutes, is limited to five guesses, and is deleted after successful verification | `invalidEmailOtpDoesNotCreateAnAccountAndIsCountedAgainstTheLimit`, `accountIsCreatedOnlyAfterCorrectEmailOtpAndTermsAcceptanceIsRecorded` |
| Hide refused access attempts | Authenticated and unauthenticated document-route denials are written in a separate `REQUIRES_NEW` transaction before returning 404 | `viewerCannotViewOrDownloadUnsharedDocumentAndAttemptIsAudited`, `unauthenticatedDocumentAttemptIsDeniedAndAudited` |
| Quietly modify or truncate audit rows | Each row is HMAC-signed over its contents and prior hash; a locked database chain-head is checked by the admin view. Successful action events share the transaction with the data change | `hmacAuditChainDetectsModifiedEventData` |
| Path traversal or overwrite using a client filename | Storage uses a random server-side key and validates that resolution remains directly within the configured storage root | `PrivateFileStorage.resolve` and server-generated UUID keys |
| Spoof a browser-supplied MIME type or upload active content for inline rendering | Content type is detected from a strict signature/encoding allowlist; downloads are attachments and `nosniff` | `uploadRejectsFileWhoseContentDoesNotMatchAllowedPdfType`; download response headers |
| CSRF an authenticated user's grant or delete action | Spring Security CSRF remains enabled; POST forms use Thymeleaf/Spring form integration; rejected document writes are audited | `csrfRejectedDocumentChangeIsAudited`; POST authorization tests use CSRF tokens |
| Enumerate document existence through error behavior | Edit submissions, grants and unauthenticated requests return 404 for both forbidden and missing IDs. Open/download/delete by a signed-in user show a "not granted" page, which reveals existence but nothing else | Authorization tests; `viewerCanAttemptToOpenFolderDocumentAndGetsAccessDeniedWhenNotGranted` |
| Abuse folder access to reach documents, or edit/replace without rights | Folder grants only list contents; edit, replace, and delegated delete require a document grant; replacement edits are audited | `FolderAccessControlTests`, `viewerCannotEditDeleteOrGrantOnUnsharedDocument` |

## Known limitations and accepted risks

* **H2 and audit-head trust boundary:** a database row lock serializes appends and successful events commit with their data changes. H2 file storage is a local/demo configuration, not a supported multi-host deployment. The chain head is in the same database, so a database administrator can roll back both the event tail and head to a previously valid prefix; a filesystem/database administrator who can also obtain the HMAC key can rewrite all events. Production evidence needs remote append-only/WORM storage or periodic externally signed chain-head anchoring, with the key held in a KMS/HSM.
* **H2 and local filesystem are a development configuration:** local storage/database corruption, host compromise, backups, encryption at rest, malware scanning, disaster recovery, and retention/deletion legal holds are not addressed. Use managed storage, encrypted volumes, backups, malware scanning, and operational access controls before real confidential data.
* **Filesystem/database transaction gap:** upload writes a private file before the metadata transaction commits (with best-effort cleanup on failure); delete removes the file before the metadata transaction commits. A storage or database failure can therefore leave an orphan file or a metadata row whose file was removed. Orphan files are not addressable through the application, but cleanup/reconciliation and a transactional object-store workflow are needed for production reliability.
* **Demo credentials and default signing key:** the application seeds known accounts on an empty database by default and has an explicitly weak local HMAC key. They are for local evaluation only. Set a unique secret and disable seeding for any network-accessible environment; HTTPS and secure session-cookie configuration must be provided by the deployment.
* **Account lifecycle and brute force:** reversible account deactivation is implemented, but login lockout, MFA, and general rate limiting are not. Deactivated users retain their grants, so reactivation restores access unless an owner separately revokes those grants.
* **Registration identity assurance and abuse:** email OTP proves access to the mailbox at registration time, not the person's legal identity or continued mailbox ownership. Registration OTP requests are cooled down per email address, but IP-level limits, CAPTCHA, and disposable-email screening are not implemented. New accounts remain VIEWER-only and receive no document access until an owner explicitly grants it.
* **Development local OTP inbox:** the `dev` profile displays registration codes instead of emailing them to support local development without SMTP. It is intended only for loopback access and does not prove mailbox ownership. Never expose this profile; deployed instances must use SMTP with local OTP disabled.
* **Login error account enumeration:** the sign-in response deliberately distinguishes a known username with an incorrect password to meet the requested UX. This reveals whether a username exists. Unknown accounts receive the generic create-account message; a production deployment should consider a generic message for both cases.
* **Password-reset OTP delivery and sessions:** email OTP reset is disabled by default and requires configured SMTP plus a separate 32-byte-or-longer secret. OTPs expire in ten minutes, are HMAC-protected at rest, and are limited to five guesses and one send per username per minute. The app does not yet apply an IP-level rate limit or revoke already-authenticated sessions after password reset; production should add both and use monitored email delivery.
* **Content validation scope:** file validation is not malware analysis and accepted PDFs/images can contain risky content. Word/Excel files may contain macros or embedded content and are not scanned; users edit them offline and re-upload. Size is capped at 10 MiB.
* **Audit coverage boundaries:** document reads/downloads and document/permission changes are recorded. Authentication failures, search queries, static CSS requests, and rejected upload attempts are not currently retained as audit events.
* **Database auto-migration:** schema is generated/updated by Hibernate; there are no versioned production migrations. Use a migration tool and reviewed migration scripts before deployment.

The automated tests cover the main cross-user access paths and audit tampering case listed above. They are not a substitute for deployment review, penetration testing, storage controls, or review of every future endpoint that handles document identifiers.
